# Stand Interface Design Principles

**Document status:** `PRELIMINARY`  
**Purpose:** Preserve reusable design guidance distilled from a conceptual design review of educational, research, and laboratory stands.  
**Scope:** Stand interface architecture and interaction organization only. This document is methodological guidance; it does not add canonical `pat-*` or `prim-*` records and does not claim empirical validation.

---

## 1. Core Design Position

A stand should be designed as a **reusable working environment**, not as a one-off screen assembled around a single experiment.

The stable stand interface provides the working surfaces and interaction mechanisms. Research-specific content, procedures, and interpretations are organized as separate modules or sessions that use those capabilities. This separation makes the interface reusable without forcing every research project into the same workflow.

The design must preserve a clear distinction between:
- the stand interface and its available capabilities;
- the active experiment or research session;
- research-specific modules and procedures;
- external publications and imported research material;
- observations, hypotheses, computational results, and verified conclusions.

These are conceptual boundaries for interface design. Their underlying data architecture and lifecycle management may belong to systems outside Atlas.

## 2. Foundational Workspace Principles

### P-01 — Dual-Workspace Principle

A general-purpose research stand interface should provide two complementary primary workspaces:

1. **Visual / Experimental Workspace** — the interactive viewport in which the user sees and manipulates the represented object, geometry, process, apparatus, or experimental state.
2. **Analytical Workspace** — the space for measurements, numerical readouts, formulas, tables, plots, spectra, logs, and derived indicators.

The two workspaces serve different cognitive tasks and should not be collapsed into one overloaded panel. Their exact contents depend on the stand domain.

### P-02 — Shared-State Coordination

The visual and analytical workspaces are different views of one active stand state. A change made in one view should be reflected in every dependent view where applicable.

Examples:
- moving a geometric construction point updates dependent measurements and plots;
- changing an experimental parameter updates the visualization and telemetry;
- selecting a time interval in a plot updates the corresponding inspection point in another view.

A shared state must have a clearly defined authority. Independent views must not silently drift into contradictory representations.

### P-03 — Adaptive Multi-Window Workspace

Primary and auxiliary workspaces should be organizable as independent windows or panels where the platform permits:
- resize, move, minimize, restore, and rearrange;
- use on one or multiple displays;
- preserve meaningful synchronization when separated across displays;
- return to a usable layout after a workspace is closed or hidden.

This is an interface-organization principle, not a requirement to use a particular windowing framework. The pattern should be evaluated against existing Atlas multi-screen and synchronized-view records before any canonical addition.

### P-04 — Stable Core, Variable Research Content

The base stand interface should remain useful as a general environment for exploration, learning, and experimentation. Research-specific procedures and content should be introduced as separate, identifiable modules rather than permanently hard-wiring one study into the base interface.

A module may configure or use available interface capabilities, but it must not imply that the base stand supports a capability that it does not actually implement.

## 3. Research Interaction Patterns

The following describe interface workflows, not a complete research-management platform.

### P-05 — Native Experiment Session

The interface should support a clearly delimited experiment session:
- identify the active configuration and relevant parameters;
- expose the controls and observations needed for the experiment;
- make it possible to capture results and the conditions under which they were obtained;
- distinguish successful, unsuccessful, invalid, incomplete, and inconclusive runs where the domain requires those states;
- allow the user to inspect prior runs without confusing them with the current live state.

A failed or invalid run is still a meaningful research outcome and should not be silently discarded.

### P-06 — External Research as a Separate Source

When a user imports another author's publication, dataset, or result, the interface should preserve its external origin. Imported claims and data must not be presented as if they were generated by the current stand or by the current researcher.

The interface should make source identity and provenance visible and distinguish:
- externally reported result;
- locally reproduced result;
- locally modified or extended experiment;
- unresolved comparison.

### P-07 — Reproduction-Oriented Comparison

Where the stand has the required capabilities, the interface may help a researcher reproduce an external result and compare it with the published reference.

A useful comparison view should expose, where available:
- source conditions and assumptions;
- local experimental conditions;
- parameter and unit differences;
- measured or computed outputs;
- deviations and missing information.

If the stand lacks a required sensor, model, control, data format, or analytical function, the interface must report the capability gap rather than simulate or imply successful reproduction.

### P-08 — Publication Analysis Workflow

An external publication can be treated as an object of structured analysis. The interface may organize extracted claims, formulas, diagrams, tables, and reported results, then link each item to a possible verification or reproduction action.

The interface must not conflate:
- what the publication claims;
- what the user has observed;
- what a computational tool has checked;
- what has been analytically or experimentally verified.

This principle complements the epistemic safeguards already described in `PATTERN_DRA.md` and `PATTERN_VADP.md`.

### P-09 — Research-to-Publication Traceability

When research results are later used in a publication, the interface should support traceable links from a presented result back to its originating experiment, configuration, parameters, and source material.

The interface should not imply that a draft, figure, or narrative statement is validated merely because it is linked to a recorded run. The validity of the claim remains dependent on its method and evidence.

### P-10 — Interactive Publication Linkage

An interactive publication may link a figure, table, construction, or claim to a corresponding stand view or reproducible procedure.

A reader should be able to move from the publication to the relevant interactive representation, inspect its parameters, and—where permitted and technically supported—replay the procedure or explore the model.

The interface must label the nature of the linked content: illustrative visualization, replay of recorded data, live experiment, numerical computation, or formal verification. These are not interchangeable.

## 4. Extensibility Boundaries

The design review identified two distinct ways in which stand capability can evolve. They must not be confused.

### E-01 — Derived Custom Stand (Outside Atlas Core Scope)

When the base stand does not provide a required capability, a user or project team may create a derived, specialized stand that adds domain-specific objects, algorithms, controls, or interface behavior.

The derived stand should retain explicit information about its origin and the differences from the base. It then evolves as a separately maintained system.

This is a broader product/software architecture concern. Atlas may catalogue interface patterns used by such a derived stand, but should not define a universal plugin, inheritance, or version-management architecture.

### E-02 — Official Core Evolution (Outside Atlas Core Scope)

The original stand may also evolve through changes approved by its owner or authorized maintainers. Such changes should preserve the core interface contract and be reviewed for compatibility, performance, usability, and regression risk.

This is distinct from arbitrary user customization. Atlas can capture the resulting interface patterns and evidence, but should not prescribe the governance or release machinery of the base product.

## 5. Epistemic and Provenance Safeguards

Interface design should make the status and origin of information legible. At minimum, avoid visually presenting these categories as equivalent:

| Category | Meaning |
|---|---|
| External claim | A statement reported by an external author or source |
| Recorded observation | Data captured during a particular session |
| Computational result | Output produced by a specified computational procedure |
| Hypothesis | A proposed explanation or relationship awaiting verification |
| Reproduced result | A result obtained locally under documented conditions |
| Verified conclusion | A claim supported by an appropriate independent verification method |

The exact status vocabulary should reuse Atlas's existing lifecycle and epistemic contracts where possible. This document does not introduce a competing status ontology.

## 6. Relationship to Existing Atlas Knowledge & Semantic Distinctions

These principles are intentionally not submitted as new canonical patterns. To prevent conceptual conflation, note the precise boundaries between high-level architectural principles and existing Atlas canonical patterns:

1. **`P-01 Dual-Workspace Principle`** defines the macro-organizational split between the **Visual / Experimental Workspace** (interacting with viewport representation/apparatus) and the **Analytical Workspace** (measurements, plots, formulas, tables, and derived indicators).
2. **`pat-reference-experiment-dual-workspace`** addresses a more specific micro-layout mechanism: side-by-side or layered comparison of a **locked baseline reference state** versus a **mutable experimental perturbation state** with delta highlighting.
3. **`pat-visual-analytical-discovery` (VADP)** governs the 7-stage interactive analytical workflow (System Decomposition -> Parametric Modeling -> Visual Analytics -> Pattern Detection [V-01..V-12] -> Hypothesis Formation -> Formal Verification -> Knowledge Extraction) across multi-curve or multi-representation views.

Initial mapping for review:

| Design principle | Likely Atlas relationship | Treatment |
|---|---|---|
| Dual visual / analytical workspaces | Macro-level split distinct from `pat-reference-experiment-dual-workspace` and `pat-visual-analytical-discovery` | Compare and reuse; avoid duplicate pattern |
| Shared-state coordination | Existing synchronized multi-screen / overview-detail patterns | Check coverage and refine only if a distinct interface problem remains |
| Adaptive multi-window workspace | Existing multi-screen patterns and layout primitives | Candidate refinement, not automatically a new canonical record |
| Parameter exploration and synchronized plots | `pat-visual-analytical-discovery` (VADP) | Reuse VADP boundary and primitives |
| Epistemic labels and provenance display | `PATTERN_DRA.md`, VADP, and existing status-display patterns | Reuse existing epistemic safeguards |
| External publication / reproduction UI | Potential future interface-pattern candidate | Keep proposed until duplicate analysis and a concrete interface problem statement exist |
| Interactive publication linkage | Potential future interface-pattern candidate | Keep proposed; distinguish replay, live execution, and verification |
| Custom stand derivation / official core evolution | Outside Atlas's strict interface-configuration scope | Do not add as Atlas canonical patterns |

## 7. Candidate Extraction Rules

A principle in this document should become a canonical Atlas pattern only when all of the following are true:

1. It describes a recurring **stand-interface** problem, not a general research-platform or software-architecture concern.
2. Its problem and solution are distinct from existing canonical patterns after a duplicate and synonym review.
3. It can be expressed using the existing Atlas ontology and required schema.
4. Its applicability, constraints, trade-offs, and required primitives can be stated concretely.
5. Its lifecycle status accurately reflects the available evidence. A conceptual proposal remains `PROPOSED`; it must not be described as tested or verified without evidence.

## 8. Non-Goals and Explicit Exclusions

This document does not specify:
- a universal research data repository or laboratory information management system;
- a general publication authoring platform;
- a universal plugin or extension framework;
- a custom-stand inheritance or version-control system;
- mathematical simulation, CAS, theorem proving, or physical safety certification;
- implementation frameworks, storage formats, APIs, or windowing libraries.

These exclusions preserve Atlas's strict focus on reusable interface configuration patterns.
